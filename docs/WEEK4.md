## Why This Week Exists at All

Week 3 produced Sigma rules. **Sigma rules don't run anywhere by themselves** — they're a vendor-neutral spec, like writing in Esperanto. To actually fire an alert you need to translate into the *vendor's* language (Splunk SPL, Elastic EQL, Loki LogQL, Falco YAML, etc).

Two paths:

1. **Translate by hand for every SIEM you adopt** — error-prone, drifts the moment a rule changes, and nobody updates all four copies.
2. **Compile automatically from Sigma → backend** — what real detection-engineering teams do. One rule file, one PR, every backend regenerated by a script.

We built path #2. That's the whole point of "Detection-as-Code."

## Part 1 — The Compilation Pipeline

### Tool: `sigma-cli` (pySigma)

**What it is:** The official Sigma project's command-line compiler. Reads `*.yml` Sigma rules, applies a *backend* (target language) and an optional *pipeline* (field-name mapping), produces queries.

**Why this and not alternatives:**

| Tool | Status | Notes |
|------|--------|-------|
| **sigma-cli (pySigma)** ✅ | Active, official | What we picked. Maintained by SigmaHQ. Supports plug-in backends. |
| `sigmac` (legacy) | **Deprecated 2023** | The original Python 2 / Python 3 compiler. Replaced by pySigma. |
| Custom Jinja templates | Possible | A few orgs do it for highly bespoke SIEMs. Reinventing the wheel for us. |
| Vendor-native (e.g. Elastic Detection Engine import) | Limited | Only goes Sigma→Elastic. We need 4 backends. |

We installed pySigma into a Python venv plus four backend plug-ins:

```bash
pip install sigma-cli                      # core compiler
pip install pysigma-backend-elasticsearch  # gives us eql + lucene
pip install pysigma-backend-splunk         # gives us spl
pip install pysigma-backend-loki           # gives us logql
```

### The Four Backends — What & Why

| Backend | Output | Used by | Why we ship it |
|---------|--------|---------|----------------|
| **eql** | Event Query Language | Elastic Security (modern Detection Engine) | Industry-standard for Elastic. Sequence/correlation support. |
| **lucene** | Kibana query syntax | Older Elastic / Kibana dashboards | Many existing Kibana dashboards still use Lucene, so we ship both. |
| **splunk** | SPL (Search Processing Language) | Splunk Enterprise, Splunk Cloud | Largest enterprise SIEM market share. |
| **loki** | LogQL | Grafana Loki | Cheap log SIEM, popular in cloud-native shops. |

We deliberately did **not** ship QRadar, Sentinel, or ArcSight backends — those need vendor-licensed environments to test against, and we'd be shipping queries we can't validate.

### The Pipeline (`scripts/compile.sh`)

```bash
./scripts/compile.sh
```

What it does, step by step:

1. **Validate** — runs `sigma check rules/` to catch YAML syntax errors before compilation.
2. **Loop** through 4 backends × 16 rules = 64 conversions.
3. **Apply pipeline** — for Elastic, `ecs_kubernetes` maps Sigma's generic `Image|endswith` to Elastic's `process.executable`. Splunk and Loki get `--without-pipeline` because their field names match Sigma's natively.
4. **Bundle Falco rules** — copies hand-authored `falco/custom-rules/*.yaml` into `dist/falco/`. (Falco isn't a Sigma backend in pySigma, so we author Falco rules directly — see Part 2.)
5. **Print summary** — successes, failures, output tree.

Final result: **64/64 conversions successful**, 0 failures.

### Output Tree

```

├── eql/         16 *.eql files     ← drop into Elastic Detection Engine
├── lucene/      16 *.lucene files  ← paste into Kibana saved searches
├── splunk/      16 *.spl files     ← saved searches in Splunk
├── loki/        16 *.logql files   ← Grafana / Loki recording rules
└── falco/       15 *.yaml files    ← Falco runtime rules (hand-authored)
```

## Part 2 — Falco Custom Rules, Live in the Cluster

Falco is the only one of our targets that **runs locally** (inside the k8s cluster, watching syscalls in real time). The others are SIEMs you query *after* logs ship to them. So Falco gets first-class treatment: we author rules **directly in Falco's YAML format** and deploy them via Helm.

### Why Hand-Author Instead of Auto-Compiling Sigma → Falco?

There **is** a community `pysigma-backend-falco`, but it's experimental, supports a narrow rule subset, and produces less idiomatic Falco than a human would write. For Falco specifically — the runtime defender we depend on most — quality > automation. The Sigma rules are still our portable source of truth; the Falco rules are the runtime mirror.

### The 15 Custom Rules (`falco/custom-rules/cyber-range-rules.yaml`)

Each rule maps one MITRE ATT&CK technique:

| ATT&CK | Rule | Detects |
|--------|------|---------|
| T1003.008 | Suspicious Read of /etc/shadow | Credential theft via shadow file read |
| T1003.001 | Read of /etc/passwd From Shell Tool | Recon-stage passwd enumeration |
| T1059.004 | Bash Reconnaissance Commands | whoami / id / hostname / uname / w / who in containers |
| T1057 | Process Discovery via ps/top | `ps -ef`, `ps aux`, `top` patterns |
| T1083 | Suspicious File Discovery via find | `find` targeting id_rsa, .env, .aws, credentials |
| T1552.004 | Search For SSH Private Keys | `~/.ssh/id_*` reads by non-SSH tools |
| T1098.004 | SSH authorized_keys Modification | Persistence via authorized_keys write |
| T1053.003 | Cron Job Modification | Writes to /etc/cron.* or /var/spool/cron/ |
| T1136.001 | Local Account Creation | useradd / adduser inside containers |
| T1548.001 | Suspicious SUID Binary Use | GTFOBins-style escapes (find -exec, vim !, python os.system) |
| T1611 | Container Escape via Host Mount | docker.sock read, cgroup release_agent write |
| T1070.003 | Bash History Tampering | rm/shred against .bash_history etc. |
| T1070.002 | Log File Deletion | Destruction of /var/log/ |
| T1071.001 | HTTP Beacon to Uncommon Port | C2 ports (4444, 5555, 8888, etc.) |
| T1505.003 | Web Shell Drop | .php/.jsp written to /var/www/, /usr/share/nginx/html/ |

### How Custom Rules Get Loaded

```bash
helm upgrade falco falcosecurity/falco -n falco \
  -f falco/values.yaml \
  --set-file customRules.cyber-range-rules\.yaml=falco/custom-rules/cyber-range-rules.yaml
```

The `--set-file` flag stuffs the YAML file's contents into Helm value `customRules."cyber-range-rules.yaml"`, which the Falco chart writes into a ConfigMap mounted at `/etc/falco/rules.d/cyber-range-rules.yaml` inside every Falco pod.

To pick up changes, restart the DaemonSet:

```bash
kubectl rollout restart daemonset/falco -n falco
```

(We turned off `watch_config_files` in `values.yaml` because Kali's default `fs.inotify.max_user_instances=128` is too low for Falco's file-watcher — we got `inotify_init1: Too many open files` flooding the logs. A rollout restart is the cleaner path on Kali.)

## The Two Gotchas That Bit Us — and Why Future-You Should Care

### Gotcha 1 — `fd.name = /etc/shadow` looks correct but never matches

```yaml
# WRONG — parses fine, fires never
condition: open_read and fd.name = /etc/shadow

# RIGHT — matches Falco's idiomatic style, fires every time
condition: open_read and fd.name in ("/etc/shadow")
```

**Why:** the `=` operator in Falco's filter language compares against literal strings, but at runtime `fd.name` is normalized through path-resolution code that compares against entries in a *list*, not a single string. Falco's own built-in rules **always** use `fd.name in (sensitive_file_names)`. If the built-ins do it that way, do it that way.

### Gotcha 2 — Falco's default `rule_matching: first` silently suppresses your rules

This one cost us 90 minutes today. The symptom:

- Falco's built-in `Read sensitive file untrusted` fired on `cat /etc/shadow`.
- Our custom `T1003.008 Suspicious Read of /etc/shadow` did **not** fire.
- Rule loaded with no errors. Compiled condition was correct. Syscall reached the engine.

**Cause:** in Falco's default `rule_matching: first` mode, only the *first* matching rule per event fires. Built-in rules load before custom rules, so the built-in always wins and your custom rule is silently skipped.

**Fix** — in `falco/values.yaml`:

```yaml
falco:
  rule_matching: all   # was: first (default)
```

Trade-off:
- `first` (default) — quieter SOCs, no duplicate alerts on the same syscall.
- `all` — every matching rule fires. **Correct for detection engineering**, where you measure coverage and verify your custom rules independently.

For a cyber-range whose entire purpose is to count detections, `all` is the only honest setting.

## End-to-End Smoke Test

Single shell command runs the whole attack suite inside the compromised pod:

```bash
kubectl exec -n cyber-range compromised-host -- sh -c '
  whoami; id; hostname; uname -a;
  cat /etc/passwd > /dev/null;
  cat /etc/shadow > /dev/null 2>&1;
  ps -ef > /dev/null;
  find / -name id_rsa 2>/dev/null > /dev/null;
'
```

Then count rule firings:

```bash
kubectl logs -n falco daemonset/falco -c falco --since=30s \
  | grep -oE '"rule":"[^"]*"' | sort | uniq -c | sort -rn
```

Result:

```
   4 "rule":"T1059.004 Bash Reconnaissance Commands"
   1 "rule":"T1083 Suspicious File Discovery via find"
   1 "rule":"T1057 Process Discovery via ps/top"
   1 "rule":"T1003.008 Suspicious Read of /etc/shadow"
   1 "rule":"T1003.001 Read of /etc/passwd From Shell Tool"
   1 "rule":"Search Private Keys or Passwords"   (Falco built-in)
   1 "rule":"Read sensitive file untrusted"      (Falco built-in)
```

**5 of our custom rules fired on the matching attacks. Zero false positives. T1611 (the noisy one from the first pass) — silent throughout.** That's the success criterion for Week 4.
